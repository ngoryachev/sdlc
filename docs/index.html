Thin SDLC orchestration on top of Claude Code. Your repo, your git, your tools — run through explicit phases, with the developer at the wheel.

the concept

Prompting is not the bottleneck.
The description is.

vague in

“add export to the report page”

Three unstated decisions, two missing edge cases, no definition of done.

vs
specified in

What, where, why, how to verify, what must not change.

The same model, the same repo — a different outcome.

So sdlc makes the description the unit of work: it is questioned, refined, approved, and only then implemented.

role separation

Four roles. Each a fresh session.

design & planning

Analyst, architect

Asks what is missing, then writes the plan: files, steps, how it will be verified.

implementation

Developer

Own worktree and branch. Writes the code, re-reads its own diff, never commits.

testing

QA engineer

New session, no memory of writing it. Runs the suite, then the thing itself. Defects go back.

review & quality

Reviewer

New session again. A verdict plus findings with severities — not a pat on the back.

The orchestrator owns git: commits, pushes, the pull request. Agents are not allowed to.

disclaimer

Not a silver bullet.

  • A good spec is required. Garbage in still gets you garbage out, only faster and with more of it.
  • Readiness is its own problem. The work surfaced an idea we now want: a skill that judges whether a task is ready to implement at all — and refuses otherwise.
  • Management still matters. Someone has to decide what is worth building, in what order, and when the answer is “not like this”. That is still a human.

What changes is where your attention goes: into the description and the decisions, not the typing.
